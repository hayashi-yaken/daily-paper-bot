## 概要

現在のボットは `assets/venues.json` に ICLR / NeurIPS / ICML の 2025 年会場のみが登録されており、2025 年の論文しか投稿されない。これを 2023〜2024 年の会場にも広げる。

あわせて、調査で判明した既存の 2 つの問題をこの機会に解消する:

1. **不採択論文も投稿対象になっている**: 現在の取得クエリ `invitation=<venue>/-/Submission` は全投稿(採択+不採択+取り下げ)を返すため、終了済みの会議では不採択論文が投稿されうる。取得を `content.venueid` フィルタに切り替えて採択論文のみに絞る。
2. **先頭 1000 件バイアス**: `/notes` API はデフォルトで先頭 1000 件しか返さないため、現状は「最初の 1000 件」からしか論文が選ばれていない。count 取得 → ランダム offset 取得の 2 段構えに変更し、全採択論文を選定対象にする(厳密な一様選定ではないが実用上ほぼ公平。通信量も約 10MB → 数十 KB に削減)。

ICLR 2023 のみ旧 OpenReview API v1 にあり対応コストが見合わないため対象外とする。追加する会場(ICLR 2024 / NeurIPS 2024・2023 / ICML 2024・2023)はすべて現行の API v2 で取得できる。

## 方針

- 「2025 年のみ」はコードではなく `venues.json` の設定データ由来。年の拡張自体は設定追加で済むが、過年度会場では不採択論文の混入が実害になるため、取得クエリの変更(採択絞り込み)をセットで行う。
- 採択絞り込みは `content.venueid=<venue>` フィルタを使う。採択論文だけが会議本体の venueid(例: `ICLR.cc/2024/Conference`)を持つため、`venues.json` の `venue` フィールドの値がそのまま使え、スキーマ変更は不要。
- ランダム選定は「count 取得 → ランダム offset で 20 件窓を取得」の 2 段構えにする。1 件だけの取得だと無効データ(タイトル欠損等)の際にリトライ処理が必要になるが、20 件窓なら既存 selector の除外ロジックで自然に吸収できる。
- ICLR 2023 は旧 API v1(別エンドポイント・invitation `Blind_Submission`・レスポンス形式が非 `{"value": ...}`)のため対象外。将来対応する場合は別チケットとする。

## 備考

- 未認証の API v2 アクセスは bot 対策(ChallengeRequiredError)で弾かれる場合があるため、ローカル動作確認には `.env` への `OR_EMAIL` / `OR_PASSWORD` 設定が必要。
- 実測済みの事実(2026-07-08 時点): ICLR 2023 は API v1 の `Blind_Submission` に 3,792 件存在。API v2 は未認証アクセスが Challenge で弾かれることを確認。
- 各会議の採択論文数は 1800〜4600 件程度のため、先頭 1000 件バイアスの解消は実質的な効果がある。
